# 08 · Deploying to Cloudflare Pages — the complete walk-through

Cloudflare Pages is the right host for this suite: **unlimited requests and bandwidth on the free
plan, commercial use allowed.** There is no traffic cap to think about, no credit metering, no
"site paused" email.

This is the whole job, start to finish, with the exact fields to fill in and the things that
usually go wrong.

**Read time: 8 minutes. Actual work: about 10 minutes, most of it waiting for the first deploy.**

---

## 0 · What you are deploying (know this before you click anything)

The folder you push to GitHub **is** the website. The repository root now contains:

```
business-dashboard-suite/          ← this folder = your GitHub repo = the site root
├── index.html                     ← THE SITE. 30 cards. Links are  demos/…  and  screenshots/…
├── 404.html                       ← served automatically for missing paths
├── _headers                       ← caching + security headers (Cloudflare reads this)
├── _redirects                     ← /portfolio → /  (kills the duplicate)
├── netlify.toml                   ← ignored by Cloudflare (kept for a Netlify fallback)
├── demos/                         ← 30 self-contained dashboard pages
├── screenshots/                   ← 30 preview images + portfolio shot
├── apps-script/                   ← source you install into Google Sheets (served, harmless)
├── docs/                          ← these guides
├── tools/                         ← rebuild scripts (not needed at runtime)
├── portfolio/index.html           ← copy with ../ links, for opening straight off disk
└── .gitignore
```

> **Why `index.html` sits at the root now.** The earlier version kept the landing page inside
> `portfolio/` and linked to `../demos/…`. That breaks on any host that publishes a *folder*:
> Point Cloudflare at `portfolio/` and `../demos/` points outside the published directory → 404 on
> every card. The root `index.html` uses `demos/…`, so the publish directory is simply the repo
> root and every link resolves. Both copies are generated by `tools/build-portfolio.js`, so they
> can never drift apart.

**Sizes:** 79 files, ~27 MB. Cloudflare's free limits are 20,000 files and 25 MiB **per file** —
the largest thing here is a 2 MB screenshot. You are nowhere near any limit.

## 2 · Put the folder on GitHub

Open a terminal **inside** `business-dashboard-suite/` (the folder that contains `index.html` — not
its parent) and run:

```bash
git init
git add .
git commit -m "30 industry dashboards — Google Sheets + Apps Script"
git branch -M main
git remote add origin https://github.com/<your-username>/business-dashboard-suite.git
git push -u origin main
```

Create the empty repo on GitHub first (**New repository → name it → don't add a README**), then the
`push` works.

**Check before you push:** the folder must contain a `.gitignore` with at least

```
node_modules/
tools/cache/
*.zip
.DS_Store
```

`node_modules` is 100+ MB — never commit it. The 28 MB ZIP should stay out too; it's your download,
not a site asset.

Verify on github.com that you can see `index.html` at the repo root, next to `demos/`.

> **Public or private repo?** Both work with Cloudflare Pages. If you'd rather people couldn't copy
> `Code.gs` and `SeedData.gs` straight from GitHub, make the repo **private** — Pages still deploys
> fine, and the site itself stays public.

## 3 · Create the Pages project

1. Go to **dash.cloudflare.com** → **Workers & Pages** in the left sidebar.
2. **Create application** → open the **Pages** tab → **Connect to Git** (labelled *Import an
   existing Git repository* on some accounts).
3. Authorise Cloudflare for GitHub if prompted. Grant access to **only this repository** — GitHub
   lets you pick "Only select repositories", and you should.
4. Select `business-dashboard-suite` → **Begin setup**.

### The build settings — this is the only part people get wrong

| Field | What to enter |
|---|---|
| **Project name** | `business-dashboard-suite` → your site becomes `business-dashboard-suite.pages.dev` |
| **Production branch** | `main` |
| **Framework preset** | **None** |
| **Build command** | *leave blank* — or type `exit 0` if your dashboard refuses a blank value |
| **Build output directory** | `/` — a single forward slash. (`/` and blank both mean "the repo root"; the docs use `/`.) |
| **Root directory** | *leave blank* |

There is nothing to compile: the HTML is already generated and the data is embedded in it. If you
put `dist` or `build` here out of habit, Cloudflare will look for a folder that doesn't exist and
give you an empty deployment — the single most common failure, and it looks like a broken site
rather than a failed build.

5. **Save and Deploy.** First deploy takes 20–40 seconds.

### What success looks like

```
✅ Cloning repository…
✅ Installing dependencies…     (skipped — nothing to install)
✅ Executing user command: …    (skipped — no build command)
✅ Uploading…     79 files
✅ Success! Your site is live at https://business-dashboard-suite.pages.dev
```

Open the URL. You should see the dark hero — *"Thirty dashboards. One spreadsheet each."* — with
30 cards grouped into 9 sections.

## 4 · Verify the deploy (2 minutes, do not skip)

| Check | Expected |
|---|---|
| Home page | 30 cards in 9 groups, thumbnails visible |
| Click any card | Dashboard opens in a **new tab**, industry switcher lists all 30 |
| `/demos/16_Boutique-Hotel-Islamabad.html` | Loads the hotel dashboard, occupancy in a big hero panel |
| `/screenshots/01_Digital-Marketing-Agency.png` | The image loads |
| `/portfolio` | 301 redirects to `/` |
| `/anything-else` | Your 404 page: "That demo moved" |
| Phone | Resize to 390 px (or open on your phone) — single column, no sideways scroll |
| Dark/light | The dashboard's own **Theme** button still works |

If a card 404s but the home page works, the publish directory is wrong (§3) or the file names in
`demos/` don't match the card links — rebuild with `node tools/build-portfolio.js` to be certain.

## 5 · Connect your own domain

Pages gives you `<project>.pages.dev` for free, forever. A custom domain is optional but worth it
for a portfolio — it's the difference between "here's my link" and "here's my site".

**In Cloudflare:** your Pages project → **Custom domains** → **Set up a custom domain** → type the
domain → **Continue**.

### Two cases

**A. The domain's DNS is already on Cloudflare** (nameservers pointed at Cloudflare)

The record is created for you. Done. Works for both `example.com` and `www.example.com`.

**B. The domain is registered elsewhere and you don't want to move DNS**

Add a CNAME at your registrar:

| Type | Name | Value | Proxy |
|---|---|---|---|
| CNAME | `www` | `business-dashboard-suite.pages.dev` | Proxied (orange cloud) |

A bare/apex domain (`example.com` with no `www`) **cannot** be pointed at Pages with a plain CNAME
at most registrars — for that, either move the domain's nameservers to Cloudflare (recommended;
free, and you keep the same registrar) or use your registrar's ALIAS/ANAME record if it has one.

### SSL

Automatic. Cloudflare issues and renews the certificate as soon as the domain shows **Active** in
Custom domains. Set **SSL/TLS → Overview → Flexible/Full** to **Full (strict)** once your origin is
Cloudflare-served (it already is), and turn on **Always Use HTTPS**.

> Give DNS up to 24 hours in the worst case, usually it's minutes. If it still says *Pending*
> after a day, the nameservers haven't propagated or a conflicting A record still exists.

## 6 · Protect the client-facing demos (optional, free)

You may not want every prospect to see all 30 demos. Cloudflare **Access** (Zero Trust) puts a
login in front of the site — free for up to 50 users:

1. Cloudflare dashboard → **Zero Trust** → **Access** → **Applications** → **Add an application**
   → **Self-hosted**.
2. Application domain: your `*.pages.dev` hostname (or your custom domain).
3. Policy: **Action: Allow**, include **Emails** → list the addresses you want to let in.

Prospects get an emailed one-time PIN. No password to manage. Keep a public copy of the site on a
second Pages project (or a `/public` subdomain) for the demos you *do* want indexed.

## 7 · Updating the site afterwards

### Normal loop

```bash
# 1. edit data or metrics
#    apps-script/Code.gs · apps-script/SeedData.gs · apps-script/Index.html
# 2. regenerate demos + portfolio + screenshots
node tools/build-demos.js          # SKIP_SHOTS=1 to skip the browser
node tools/build-portfolio.js
# 3. publish
git add . && git commit -m "rebalance pharmacy stock cover"
git push
```

Cloudflare sees the push and redeploys in about 30 seconds. Static assets are cached at the edge;
`_headers` sets HTML to `must-revalidate` and the screenshots to a one-year immutable cache, so
visitors get fresh pages but don't re-download 25 MB of PNGs on every visit.

### Previews

Any branch other than `main` gets its own preview URL
(`<branch>.business-dashboard-suite.pages.dev`) — good for showing a client a change before it
goes live. Pull requests get a comment with the preview link automatically.

### Rollback

**Deployments** tab → find the last good one → **⋯ → Rollback**. Instant, no rebuild.

### Editing without Git

You can edit files directly on github.com (pencil icon → commit). That counts as a push, so Pages
redeploys. Fine for a typo; use the build scripts for anything that touches the data.

## 8 · No GitHub? Upload the folder directly

You lose auto-deploy on push, but it's two commands and needs no repo:

```bash
cd business-dashboard-suite
npx wrangler pages deploy . --project-name=business-dashboard-suite
```

The first run opens a browser to authorise Cloudflare. Every later run uploads the current folder
as a new deployment. Direct uploads don't consume builds at all.

You can also drag a folder onto **Workers & Pages → Create → Pages → Upload assets** in the
dashboard. Same result.

| Resource | Free plan | What it means here |
|---|---|---|
| Requests / bandwidth (static) | **Unlimited** | A viral reel costs you nothing |
| Builds | 500 / month, 1 at a time, 20-min timeout | You'd need 16 pushes a day to hit it |
| Files per deployment | 20,000 | You have 79 |
| Max single file | 25 MiB | Largest is ~2 MB |
| Custom domains | 100 per project | — |
| Projects | 100 per account | — |
| `_headers` rules | 100 | You use 3 |
| `_redirects` rules | 2,000 static + 100 dynamic | You use 2 |
| Access (password protection) | 50 users | Plenty for client previews |
| Pages Functions | Workers free quota (100k requests/day) | Unused — this site has no server code |

**Cost: Rs 0.** No metering, no pause, no card. That is the whole reason to prefer Cloudflare over
Netlify's credit model once you start promoting the site.

> One more useful option for later: **Cache Rules → Tiered Cache** and **Speed → Brotli** are on by
> default for `pages.dev`; nothing to configure.

## 10 · Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| Build "succeeds" but the site is empty / 404 at `/` | Build output directory isn't the root | Settings → Builds & deployments → set **Build output directory** to `/`, redeploy |
| Home page works, every card 404s | `../demos/` paths (old `portfolio/index.html` published) | Publish the repo root, not `portfolio/`; or run `node tools/build-portfolio.js` |
| Thumbnails missing, cards fine | `screenshots/` not committed | `git add screenshots && git commit` — check `.gitignore` isn't swallowing it |
| Images break only in production | Filename case mismatch (`Caf` vs `caf`) | macOS is case-insensitive, Cloudflare isn't. Rename to match the card link exactly, rebuild |
| Build log: *Failed: build command exited with 1* | A build command was entered | Clear it, or use `exit 0` |
| Site shows an old version | Browser/edge cache | Hard-refresh; confirm the deployment timestamp in the Pages dashboard |
| `/portfolio` still visible | `_redirects` not uploaded | Confirm `_redirects` is at the repo root and redeploy |
| Custom domain stuck on *Pending* | DNS conflict | Remove any existing A/CNAME for that name; for apex, move nameservers to Cloudflare |
| 404 with the wrong styling | `404.html` missing from the deployment | It's at the repo root — redeploy |
| Everything 403s | Cloudflare Access policy too tight | Zero Trust → Access → check the policy's include rules |

## 11 · What to do differently for a *real client*

The portfolio is a static site; a client's install is not:

| | Portfolio demo | Client install |
|---|---|---|
| Where it runs | Cloudflare Pages | Google Apps Script web app |
| URL | `yoursite.pages.dev` | `script.google.com/macros/s/…/exec` |
| Data | embedded in the HTML | read live from the client's sheet |
| Access | public (or Access PIN) | Google account / link sharing |
| You update it by | pushing to Git | the client edits the sheet |

So: **Cloudflare hosts what you show, Google hosts what they use.** Don't try to make Pages serve
the live dashboard — the dashboard needs the Sheet, and the Sheet is on Google.
